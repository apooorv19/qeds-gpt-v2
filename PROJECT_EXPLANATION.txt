QEDS-GPT PROJECT EXPLANATION
============================

This document explains the QEDS-GPT project from start to end in a chronological,
architecture-first way. It is written for someone who wants to understand how the
whole system works without constantly opening every source file.


1. PROJECT SUMMARY
==================

QEDS-GPT is a Hybrid Retrieval-Augmented Generation application for academic
question answering over Quantitative Economics and Data Science semester notes.

The system lets a user ask questions through a Streamlit chat interface. The
question is sent to a FastAPI backend. FastAPI does not run the RAG pipeline
directly. Instead, it creates a background job and places it into a Redis-backed
RQ queue. A worker process picks up the job, runs the existing RAG pipeline,
stores the result, and the Streamlit frontend polls until the answer is ready.

The core RAG pipeline uses:

- ChromaDB as the persisted vector database.
- HuggingFace embeddings using BAAI/bge-m3.
- Dense vector retrieval.
- BM25 keyword retrieval.
- Reciprocal Rank Fusion to combine retrieval results.
- Groq LLM for classification, summarization, and answer generation.
- Streamlit session state for frontend conversation memory.
- Redis and RQ for asynchronous job execution.
- Optional Pydantic Logfire observability for tracing API and worker stages.

3. WHY THIS ARCHITECTURE EXISTS
===============================

Originally, the application was a normal synchronous Streamlit RAG app. That
means Streamlit accepted a user question and directly ran classification,
retrieval, LLM generation, and UI rendering in one flow.

That works for demos and small usage, but it has limitations:

- One long LLM call can block the user interface.
- Multiple users can cause slowdowns.
- Retrieval and LLM calls are expensive and may take several seconds.
- There is no clean separation between frontend, API, and execution layer.
- It is harder to monitor where time is being spent.

The newer architecture separates responsibilities:

- Streamlit is only the frontend.
- FastAPI is the API layer.
- Redis is the queue and job-state backend.
- RQ workers execute expensive RAG jobs in the background.
- The RAG modules remain unchanged and reusable.

This makes the system closer to a production AI backend.

5. MAJOR COMPONENTS
===================

5.1 Streamlit Frontend
----------------------

Main file:

src/streamlit_app.py

The Streamlit frontend is responsible for:

- Rendering the QEDS-GPT title and sidebar.
- Rendering previous chat messages.
- Accepting the user's current question.
- Sending the question to FastAPI.
- Receiving a job_id immediately.
- Polling the FastAPI result endpoint every second.
- Displaying the final answer when the job is completed.
- Saving the answer, sources, and retrieved chunks in frontend memory.

Important detail:

Streamlit does not call the LLM or retriever directly anymore. It behaves like a
client of the FastAPI backend.


5.2 FastAPI Backend
-------------------

Main files:

src/api/main.py
src/api/routers/chat.py
src/api/routers/health.py
src/api/routers/version.py
src/api/models.py

FastAPI is responsible for:

- Defining API endpoints.
- Validating request bodies using Pydantic models.
- Enqueueing chat jobs into Redis/RQ.
- Returning job_id immediately.
- Providing result polling endpoints.
- Providing health/version endpoints.

The API does not directly execute LLM inference or retrieval.


5.3 Redis and RQ Queue
----------------------

Main file:

src/job_queue.py

Redis stores the queue and job metadata. RQ is the Python job queue library that
uses Redis.

When FastAPI receives a chat request, it calls:

queue.enqueue("worker.process_chat_job", payload)

This creates a job in Redis. The job receives a unique job_id. FastAPI returns
that job_id to the frontend.


5.4 Background Worker
---------------------

Main file:

src/worker.py

The worker listens to the Redis queue. When a job appears, the worker:

1. Marks the job as running.
2. Loads/reuses RAGService.
3. Classifies the query.
4. If needed, runs hybrid retrieval.
5. Builds the prompt.
6. Calls Groq.
7. Creates the final result object.
8. Stores the result in Redis through RQ.
9. Marks the job as completed.

On Windows, worker.py uses RQ SimpleWorker because the default RQ Worker uses
Unix-only fork behavior. On Linux/Docker, it uses the normal Worker.


5.5 RAG Service
---------------

Main file:

src/services.py

RAGService is the business logic layer. It coordinates:

- LLMService
- QueryClassifier
- HybridRetriever
- Prompt construction
- Immediate responses
- Academic answer generation

It intentionally does not know about Streamlit widgets, FastAPI endpoints, or
Redis internals. This separation keeps the RAG pipeline reusable.


5.6 Retriever
-------------

Main file:

src/retriever.py

The retriever is responsible for:

- Loading ChromaDB.
- Loading HuggingFace embeddings.
- Building the dense vector retriever.
- Building the BM25 retriever.
- Running both retrievers.
- Combining results with Reciprocal Rank Fusion.
- Applying semester filters.
- Returning top documents.


5.7 LLM Client
--------------

Main file:

src/llm.py

LLMService wraps Groq. It reads GROQ_API_KEY from environment variables or
Streamlit secrets. It sends messages to the configured Groq chat model.

Default model:

llama-3.1-8b-instant


5.8 Memory
----------

Main file:

src/memory.py

ChatManager stores frontend conversation memory using Streamlit session state.
It stores:

- User messages.
- Assistant messages.
- Optional sources.
- Optional retrieved chunks.
- Whether retrieval was used.
- Conversation summary.
- Turn count.

Important distinction:

FastAPI is stateless. The frontend sends chat history to FastAPI with each job.
Streamlit session state is used only for the frontend user's current session.


5.9 Observability
-----------------

Main file:

src/observability.py

The project optionally integrates Pydantic Logfire. Logfire is used as a
complement to standard Python logging.

It traces:

- API job enqueueing.
- API result polling.
- Worker classification.
- Worker retrieval.
- Worker LLM generation.

It intentionally does not record:

- Full prompts.
- Retrieved note text.
- Chat history content.
- LLM answer text.
- API keys.

This protects sensitive user conversations and academic note content.


6. CHRONOLOGICAL STARTUP FLOW
=============================

To run the full async system locally, four processes are involved.

Step 1: Start Redis
-------------------

Redis must run first because both FastAPI and the worker need it.

Example:

docker run -p 6379:6379 redis:7-alpine

Redis listens on:

localhost:6379


Step 2: Start Worker
--------------------

The worker listens for jobs.

Example on Windows PowerShell:

cd "D:\GEN AI\qeds-gpt-refactored-hf"
..\venv\Scripts\Activate.ps1
$env:GROQ_API_KEY="your_key"
$env:REDIS_URL="redis://localhost:6379/0"
python src/worker.py

Expected log:

Worker listening on queue: qeds-rag-jobs
Using worker class: SimpleWorker


Step 3: Start FastAPI
---------------------

FastAPI exposes API endpoints.

Example:

cd "D:\GEN AI\qeds-gpt-refactored-hf"
..\venv\Scripts\Activate.ps1
$env:GROQ_API_KEY="your_key"
$env:REDIS_URL="redis://localhost:6379/0"
uvicorn api.main:app --app-dir src --reload

FastAPI docs:

http://localhost:8000/docs


Step 4: Start Streamlit
-----------------------

Streamlit is the frontend.

Example:

cd "D:\GEN AI\qeds-gpt-refactored-hf"
..\venv\Scripts\Activate.ps1
$env:QEDS_API_URL="http://localhost:8000/api/v1"
streamlit run src/streamlit_app.py

Streamlit opens in the browser.


7. CHRONOLOGICAL REQUEST FLOW
=============================

This section explains what happens when a user asks a question.

Example question:

"Explain the Lorenz curve."


Step 1: User enters question
----------------------------

The user types the question in Streamlit:

Explain the Lorenz curve.


Step 2: Streamlit gathers chat history
--------------------------------------

Streamlit calls:

chat_manager.get_context_messages()

This returns recent conversation history from Streamlit session state. If the
conversation has a summary, that summary is included too.


Step 3: Streamlit submits job to FastAPI
----------------------------------------

Streamlit calls:

submit_chat_job(message, semester_filter, history)

This sends a POST request to:

POST /api/v1/chat

Example request:

{
  "message": "Explain the Lorenz curve.",
  "semester_filter": null,
  "history": []
}


Step 4: FastAPI validates the request
-------------------------------------

FastAPI uses Pydantic models from src/api/models.py.

The request is validated as ChatRequest:

- message must be a non-empty string.
- semester_filter may be null or an integer from 1 to 6.
- history must be a list of chat messages.


Step 5: FastAPI enqueues the job
--------------------------------

FastAPI does not call Groq or ChromaDB directly.

It calls:

queue.enqueue("worker.process_chat_job", request_payload)

Redis stores the job.

FastAPI immediately returns:

{
  "job_id": "4b4bfd84-e838-4e7b-8319-1f0909525639",
  "status": "queued"
}


Step 6: Streamlit stores pending job
------------------------------------

Streamlit stores:

- job_id
- user_query
- submitted_at timestamp

in st.session_state.pending_job.

Then Streamlit reruns the page.


Step 7: Streamlit polls for result
----------------------------------

On each rerun, Streamlit checks whether pending_job exists.

If yes, it calls:

GET /api/v1/result/{job_id}

If the job is queued or running, Streamlit waits one second and reruns.

The UI remains responsive in the sense that the RAG work is not being performed
inside Streamlit. Streamlit is only polling the backend.


Step 8: Worker receives the job
-------------------------------

The worker process is already listening to Redis.

When the job appears, the worker logs:

Job started: 4b4bfd84-e838-4e7b-8319-1f0909525639

The worker marks the job metadata as running.


Step 9: Worker creates or reuses RAGService
-------------------------------------------

The worker calls:

get_worker_rag_service()

This uses lru_cache so one RAGService instance is reused inside the worker
process.


Step 10: Query classification
-----------------------------

The worker calls:

rag_service.classify_query(message, context_messages)

The classifier uses Groq to classify the query into:

- ACADEMIC
- GREETING
- META
- GENERAL
- INJECTION

For "Explain the Lorenz curve.", the expected category is:

ACADEMIC


Step 11: Immediate response check
---------------------------------

If the category is GREETING, META, GENERAL, or INJECTION, the worker may return
an immediate non-retrieval answer.

For example:

User: Hello

The system can answer directly without loading ChromaDB or BM25.

For "Explain the Lorenz curve.", the category is academic, so retrieval runs.


Step 12: Hybrid retrieval
-------------------------

The worker calls:

rag_service.retrieve(message, semester_filter)

This enters HybridRetriever.

HybridRetriever performs two searches:

1. Dense retrieval
2. BM25 retrieval


Step 13: Dense retrieval
------------------------

Dense retrieval uses:

- HuggingFaceEmbeddings
- BAAI/bge-m3
- ChromaDB

The query is embedded into a vector. ChromaDB compares that query vector with
stored note chunk embeddings and returns semantically similar chunks.

This is useful when the user asks a question in different words from the notes.


Step 14: BM25 retrieval
-----------------------

BM25 retrieval searches for keyword overlap.

This is useful for exact academic terms such as:

- Lorenz curve
- Gini coefficient
- OLS
- covariance
- Pareto distribution
- hypothesis testing

BM25 helps preserve exact vocabulary matches that dense retrieval might soften.


Step 15: Reciprocal Rank Fusion
-------------------------------

The dense retrieval results and BM25 results are two ranked lists.

They cannot be merged by raw score because their scores mean different things.

The project uses Reciprocal Rank Fusion:

score = sum(1 / (rank + c))

This rewards chunks that appear high in either or both retrievers.


Step 16: Semester filter
------------------------

If the user selected a semester filter in the sidebar, the retriever removes
documents whose metadata semester does not match.

If no filter is selected, all semesters are considered.


Step 17: Prompt construction
----------------------------

The worker calls:

rag_service.build_academic_answer(message, docs, context_messages)

This:

1. Formats retrieved chunks with source labels.
2. Cleans text using text_processor.clean_text().
3. Truncates context to MAX_CONTEXT_CHARS.
4. Adds recent chat history.
5. Builds the final academic prompt.

The prompt tells the model:

- Be academically accurate.
- Use LaTeX for equations.
- Rely on retrieved notes.
- If notes do not contain the answer, say so and use general knowledge.
- Do not hallucinate citations.


Step 18: Groq LLM call
----------------------

LLMService sends the prompt to Groq.

Default model:

llama-3.1-8b-instant

The LLM returns the final answer.


Step 19: Worker builds final result
-----------------------------------

The worker returns a result object like:

{
  "answer": "The Lorenz curve is ...",
  "category": "ACADEMIC",
  "used_retrieval": true,
  "sources": [
    {"label": "Economics - Inequality - Semester 3"}
  ],
  "retrieved_chunks": [
    {
      "index": 1,
      "source": "Economics - Inequality - Semester 3",
      "content_preview": "The Lorenz curve represents ...",
      "metadata": {...}
    }
  ]
}

RQ stores this result in Redis.


Step 20: Streamlit receives completed result
--------------------------------------------

Streamlit polls:

GET /api/v1/result/{job_id}

Now the response is:

{
  "job_id": "...",
  "status": "completed",
  "answer": "...",
  "category": "ACADEMIC",
  "used_retrieval": true,
  "sources": [...],
  "retrieved_chunks": [...]
}


Step 21: Streamlit renders the answer
-------------------------------------

Streamlit displays:

- The assistant answer.
- Sources Used.
- View Retrieved Chunks expander.

The retrieved chunks are shown only when used_retrieval is true.

If the model used general knowledge because the notes did not contain the topic,
sources are hidden.


Step 22: Streamlit updates memory
---------------------------------

Streamlit calls:

chat_manager.add_turn(...)

It stores:

- user message
- assistant answer
- sources
- retrieved chunks
- used_retrieval flag

This is why sources and retrieved chunks remain visible even after Streamlit
reruns.


8. EXAMPLE FULL WALKTHROUGH
===========================

User asks:

"Explain the Lorenz curve."

Expected chronological behavior:

1. Streamlit displays the user message.
2. Streamlit sends POST /api/v1/chat to FastAPI.
3. FastAPI validates the request.
4. FastAPI enqueues job in Redis.
5. FastAPI returns:

   job_id = "abc-123"
   status = "queued"

6. Streamlit stores the pending job.
7. Streamlit polls GET /api/v1/result/abc-123.
8. Worker picks the job.
9. Worker classifies it as ACADEMIC.
10. Worker runs dense retrieval.
11. Worker runs BM25 retrieval.
12. Worker fuses results using RRF.
13. Worker builds context and prompt.
14. Worker calls Groq.
15. Worker stores result in Redis.
16. Streamlit polls again and sees completed.
17. Streamlit displays the final answer.
18. Streamlit displays sources and retrieved chunks.
19. Streamlit saves the full turn in memory.


9. FOLLOW-UP QUESTION EXAMPLE
=============================

After the previous question, the user asks:

"What is its formula?"

The word "its" refers to the Lorenz curve.

Chronological behavior:

1. Streamlit sends recent chat history with the new question.
2. FastAPI queues the job.
3. Worker receives the job.
4. Classifier sees the chat history.
5. The query is classified as ACADEMIC.
6. Retrieval uses the current question plus context-aware classification.
7. The LLM receives chat history and retrieved notes.
8. The final answer explains the Lorenz curve formula.

This is possible because the frontend sends history to the backend and memory is
stored in Streamlit session state.


10. CONCURRENT REQUEST HANDLING
===============================

The architecture supports multiple users because FastAPI does not block while
the LLM runs.

Example:

Question A
Question B
Question C

FastAPI receives all three questions and quickly creates three jobs:

Job A -> Redis
Job B -> Redis
Job C -> Redis

Workers then process jobs.

If one worker is running:

Job A runs first, then B, then C.

If three workers are running:

Worker 1 -> Job A
Worker 2 -> Job B
Worker 3 -> Job C

This is how the system scales horizontally.

To start multiple workers locally:

Terminal 1:
python src/worker.py

Terminal 2:
python src/worker.py

Terminal 3:
python src/worker.py

Each worker listens to the same Redis queue.

13. ERROR HANDLING
==================

FastAPI errors:

- If Redis is unavailable, POST /chat returns 503.
- If a job_id does not exist, GET /result/{job_id} returns 404.

Worker errors:

- The worker logs the exception.
- The job metadata is marked as error.
- The result endpoint returns status = error.

Streamlit errors:

- If FastAPI cannot be reached, Streamlit shows an API unavailable message.
- If polling fails, Streamlit retries.
- If the job fails, Streamlit displays the error message.


14. SECURITY CONSIDERATIONS
===========================

API keys:

- GROQ_API_KEY should not be committed.
- Use environment variables or .streamlit/secrets.toml locally.

Prompt and note privacy:

- Do not log full prompts.
- Do not log retrieved note text.
- Do not send raw conversation content to observability tools unless explicitly
  needed and approved.

Prompt injection:

- The classifier includes an INJECTION category.
- Injection-style requests receive refusal responses.

General knowledge fallback:

- If the answer is not found in notes, the model can answer from general
  knowledge.
- Sources are hidden in that case to avoid false citations.

17. INTERVIEW EXPLANATION
=========================

If asked to explain this project in an interview:

"QEDS-GPT is a production-style Hybrid RAG academic assistant. The frontend is
Streamlit, but the actual backend is FastAPI. FastAPI does not run LLM calls
directly. It queues jobs in Redis using RQ and immediately returns a job_id.
Background workers consume jobs, run the existing RAG pipeline, retrieve context
from ChromaDB using both dense retrieval and BM25, fuse results with Reciprocal
Rank Fusion, call Groq for the final answer, and store the result. Streamlit
polls the result endpoint and displays the answer with sources and retrieved
chunks. This design prevents long LLM calls from blocking the API and allows
multiple workers to process concurrent user questions."


18. COMMON INTERVIEW QUESTIONS
==============================

Question: Why use Redis and RQ?

Answer: Redis provides a fast external queue that can be shared between FastAPI
and worker processes. RQ is simple and Pythonic. It is sufficient for this
stage because we need background job execution without adding Celery-level
complexity.


Question: Why not asyncio.Queue?

Answer: asyncio.Queue is in-memory and process-local. It would not work well
when Streamlit, FastAPI, and workers are separate processes. Redis gives shared
state across services.


Question: Does FastAPI execute the RAG pipeline?

Answer: No. FastAPI only validates the request, enqueues a job, and exposes
polling endpoints. The worker executes RAG.


Question: How does the system handle multiple users?

Answer: Each request becomes a separate job in Redis. Multiple workers can
consume jobs concurrently. This prevents one user's long LLM call from blocking
another user's request at the API layer.


Question: Why use BM25 and dense retrieval together?

Answer: BM25 preserves exact keyword matching, while dense retrieval captures
semantic similarity. Hybrid retrieval improves recall for academic notes.


Question: Why use Reciprocal Rank Fusion?

Answer: BM25 and dense retrieval scores are not directly comparable. RRF merges
ranked lists based on positions instead of raw scores.


Question: Does the project store user data permanently?

Answer: Streamlit session memory is temporary. RQ stores job results in Redis
for a configured TTL. There is no permanent user database yet.


Question: What would be the next production improvements?

Answer: Authentication, rate limiting, persistent user sessions, robust retry
policies, circuit breakers, structured metrics, retrieval evaluation, and
deployment hardening.


19. FINAL SUMMARY
=================

QEDS-GPT started as a working synchronous Streamlit RAG app. It has evolved into
a modular, asynchronous, queue-based RAG system:

- Streamlit handles user interaction.
- FastAPI handles API contracts.
- Redis/RQ handles job queues.
- Workers execute expensive RAG logic.
- ChromaDB stores vectorized notes.
- HuggingFace embeddings power semantic retrieval.
- BM25 preserves keyword retrieval.
- RRF combines retrieval results.
- Groq generates the final response.
- Logfire optionally traces API and worker stages.

The application preserves the original Quantitative Economics and Data Science
RAG pipeline while improving scalability, maintainability, and production
readiness.
